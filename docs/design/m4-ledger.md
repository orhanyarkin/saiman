# M4 design contract — ledger and reconciliation

Binding for every M4 task. Source: architect pass (2026-10-01) and the human's decisions: outbox with **Spring Modulith** (not hand-rolled), property tests with seeded JUnit 5 generators (jqwik ruled out, ADR-0019), settle-first split into **M4b**, seller-api gets schema `seller_api`, ledger HTTP uses the orchestrator guard posture (authn in M6), chain reads only via the public `https://sepolia.base.org`. ADRs: 0016, 0017, 0018 (+ ADR-0013 amendment), 0019, ADR-0015 amendment.

**Acceptance (PLAN.md):** balanced-postings property test passes; duplicate and out-of-order events handled; a deliberately corrupted record shows up as a mismatch in the report.

## Standing rules
1. Money is integer atomic units; testnet only (`eip155:84532`, chain id 84532 checked at startup); no secret, signature or idempotency key in events, logs or spans; nonces only in `payments.*`.
2. Every state change that emits an event publishes it through Spring Modulith's registry in the same transaction (ADR-0016); every consumer dedupes through `InboxGuard` in the same transaction as its postings; consumers are order-independent.
3. Decisions that release budget or declare a mismatch read the chain at the `safe` block; an RPC failure is "skip", never a mismatch; HELD stays counted until resolved (fail closed).
4. The spend plane consumes nothing from Kafka (Redpanda has no auth).
5. Hermetic CI: chain calls are stubbed; live chain tests are `@Tag("testnet")` and excluded from `check`.
6. Every task report ends with "Spring notes".

## Producers
- **Orchestrator** (`V6__payment_events.sql`): Modulith `event_publication` table in schema `orchestrator`; `payment_intent` gets `resolved_by text check in ('FACILITATOR','CHAIN')`, `resolved_at timestamptz`, and a partial unique index on `(lower(payer), lower(auth_nonce)) where auth_nonce is not null`. Publish `PaymentAuthorized` in the transaction that marks an intent SIGNED (`markSigned` becomes transactional together with the publication), `PaymentSettled` (BUYER, FACILITATOR) in `BudgetSpendGuard.commit`, and from `HeldPaymentResolver` either `PaymentSettled` (CHAIN) or `PaymentFailed` (FINAL, `expired_unused`). `agent.run-step.v1`: externalize each appended `run_event` (key run id). `V7__backfill_payment_events.sql` (or an idempotent startup backfill) publishes events for existing SIGNED/SETTLED/HELD intents so M3 history reconciles.
  - *As built (T4):* routing is an `EventExternalizationConfiguration` bean (the shared records can't carry `@Externalized`); values are String JSON from a `StringJacksonJsonMessageConverter` without `__TypeId__` (same as the ledger); a run step's value is its SSE envelope. Each (intent, kind) is published at most once through `payment_event_log` (V6), with event id `UUID.nameUUIDFromBytes("saiman:orchestrator:payments:<intentId>:<KIND>")`; the backfill is a startup `ApplicationRunner` (after `SpendRecovery`) that publishes what has no log row. Incomplete publications are resubmitted every `saiman.orchestrator.outbox.resubmit-interval` (gauge `saiman.outbox.incomplete`). `RunEventBus`/`ApprovalWaiter` are plain `@EventListener`s deferring to `afterCommit`: Modulith's `CompletionRegisteringAdvisor` wraps every AFTER_COMMIT `@TransactionalEventListener` regardless of the registry trigger and opens a `REQUIRES_NEW` transaction, which starved the pool under concurrent appends. The resolver skips (does not settle blind) when the tx-log lookup fails, and also skips HELD intents with no recorded nonce (logged).
- **HeldPaymentResolver** (orchestrator, `saiman.orchestrator.held-resolution: {interval: 2m, batch-size: 20}`): for HELD intents whose `valid_before` is before the `safe` block's timestamp, read `authorizationState` at that block; true → SETTLED (reserved → committed under the existing lock order; tx from `findAuthorizationTx`, else null) ; false → RELEASED (reserved released). RPC failure → untouched.
- **seller-api** (`V1__seller_schema.sql`, schema `seller_api`, first Flyway use in seller-api): `settlement(payment_key pk, tx_hash, amount_atomic, pay_to, payer, outcome, created_at)` + Modulith registry; an `@EventListener` on the starter's settled/failed events writes the row and publishes `PaymentSettled` (SELLER, FACILITATOR) or `PaymentFailed` (SELLER, AMBIGUOUS, bounded reason) in one transaction. A database failure must not fail the paid response already settled: log + metric.
  - *As built (T6):* package `sellerapi.settlement`. `SettlementRecorder` has two plain `@EventListener`s (settled/failed starter events) and does everything in one `TransactionTemplate` transaction: `INSERT ... ON CONFLICT (payment_key) DO NOTHING`, and only when a row was inserted `publishEvent(PaymentSettled|PaymentFailed)`. Event ids are `UUID.nameUUIDFromBytes("saiman:seller-api:payments:<paymentKey>:SETTLED|FAILED")`, correlation id is the current trace id, else the first 32 hex chars of SHA-256 of the payment key. `V1__seller_schema.sql` also carries `settlement.reason_code` (the bounded failure code). Any `RuntimeException` is caught, logged by class name only and counted in `saiman.seller.settlement_record_failures`; the paid response is unchanged. Hikari `connection-timeout` is 2000 ms so a dead database cannot hold a paid response for the default 30 s. Routing, String JSON converter, topics (1 partition) and the `saiman.outbox.incomplete` gauge/resubmitter mirror the orchestrator (`saiman.seller.outbox.*`). Tests import one shared `TestcontainersConfiguration` (Postgres) into every `@SpringBootTest`.

## Ledger (`services/ledger`, schema `ledger`)
- Tables (V1): `account(code, book, type, asset, decimals, wallet, unique(code, asset))`; `journal_entry(id, payment_id, payment_key, book, kind, source_event_id, reverses_entry_id, description, effective_at, recorded_at)` with a partial unique index `(payment_key, book, kind)` for ENCUMBER/SETTLE/RELEASE/SALE/CREDIT_NOTE; `posting(id identity, entry_id, account_code, side, amount_atomic > 0, asset, decimals)`; deferred constraint trigger (≥2 postings, Σdebit = Σcredit per asset at commit); immutability triggers; `payment` projection (buyer_state NONE/AUTHORIZED/SETTLED/RELEASED, seller_state NONE/SETTLED/SETTLE_FAILED, chain_state UNKNOWN/USED/UNUSED, tx hashes, valid_before, last_checked_at); `reconciliation_run`, `reconciliation_mismatch(unique(payment_id, kind))`; `inbox`; Modulith registry for the ledger's own events.
- Consumers: `@KafkaListener` per `payments.*` topic, String payload parsed with Boot's `JsonMapper` into the shared records (no type headers), `@Transactional`, record ack mode; `InboxGuard` first; then the pure state machine produces entries; publish `EntryPosted` per entry. Poison messages go to `<topic>.ledger-dlt`.
- Accounting (ADR-0017) — worked examples: settled 0.02 call → ENCUMBER (Dr buyer encumbered / Cr buyer available 20000), SALE (Dr seller wallet / Cr seller revenue 20000), SETTLE (Dr buyer expense / Cr buyer encumbered 20000); HELD then released → ENCUMBER then RELEASE, net 0; approval rejected → no entries; corrupted SALE (25000 instead of 20000) → reconciliation posts ADJUSTMENT Dr suspense 5000 / Cr seller wallet 5000 and an AMOUNT_MISMATCH.
- Reconciliation (`saiman.ledger.reconciliation: {interval: 5m, grace-after-valid-before: 30m, receipt-grace: 10m, batch-size: 50}`): single runner (`pg_try_advisory_lock`); read `safe`; internal checks; select due payments; per payment in its own transaction fetch receipts / `authorizationState` / log lookup, feed the same state machine, write mismatches, adjustments and events; run status COMPLETED or PARTIAL (RPC skips).
- As built in T3: `EntryPosted` lives in `libs/shared` (no Modulith dependency), so it is routed to `ledger.entry-posted.v1` (key payment id) by an `EventExternalizationConfiguration` bean instead of `@Externalized`; Kafka payloads are String JSON without `__TypeId__` headers (`spring.modulith.events.kafka.enable-json=false` + a String JSON converter). Payment and entry ids are name-based UUIDs of the payment key (and book/kind), so replays reproduce them. Facts whose amount, payTo or validBefore contradict the recorded authorization are rejected to `<topic>.ledger-dlt` (`ConflictingFactException`). RELEASED then SETTLED (contradictory producers) posts SETTLE plus a REVERSAL of the RELEASE. Trial balance: a bare JSON array of `{account, book, type, asset, decimals, debit, credit, balance}`, `balance = debit - credit` (integers).
- As built in T5: the chain step is a pure sibling of `PaymentBook` (`reconciliation.ChainReconciler`; precedence table in its Javadoc). `V2__reconciliation.sql` adds `payment.chain_block` and `reconciliation_item(run_id, payment_id, status, tx_hash, mismatch_kind, ledger/chain amounts, adjustment_entry_id)` so a report lists MATCHED and PENDING items. **Due payments** = every payment with a reported tx hash plus every payment past `valid_before + grace-after-valid-before`, least recently checked first (batch <= 50); matched payments stay due, so a record tampered after its first check is still caught (the live tamper demo needs this). **Known wallets**: the buyer wallet is compared once the buyer book is terminal (SETTLED/RELEASED), the seller wallet once the seller book reported (SETTLED/SETTLE_FAILED); an unreported book is not compared (M3 history is buyer-only). The comparison uses the net over all of the payment's entries (adjustments included), which makes reruns post nothing; one ADJUSTMENT entry per payment and run (book PLATFORM, id derived from payment key + run id). Mismatch naming is `<books>_BUT_<chain>`: SETTLED_BUT_UNUSED (books moved money, chain unused), UNUSED_BUT_SETTLED (books released/failed, chain used). TX_NOT_FOUND once the safe block is past `valid_before + receipt-grace` (a transfer cannot be mined after validBefore; no reported-at column needed). Chain reads happen outside the item transaction (no row lock across RPC latency); the item transaction re-locks the row and the pure step answers PENDING if the evidence no longer covers it. `findAuthorizationTx` searches `min(log-search-blocks = 3600, max-log-range-blocks)` blocks ending just after the estimated block of validBefore, once per payment (a used authorization without a tx stays TX_UNKNOWN without re-scanning). Run status FAILED when the safe block itself is unavailable. Report JSON as below plus `suspenseSide` (DEBIT/CREDIT/null) because `Money` is never negative; `suspense` is the absolute balance when the report is read. Mismatches are recorded and published once per (payment, kind); a later adjustment under an existing kind is linked from the run item only. The scheduler is a `SchedulingConfigurer` registered only when a `BaseSepoliaUsdc` bean exists; the ledger defaults `saiman.chain.rpc-url` to `https://sepolia.base.org` (`SAIMAN_CHAIN_RPC_URL`).
- HTTP (guarded like orchestrator `/api`): `GET /api/v1/ledger/trial-balance`, `POST /api/v1/reconciliation/runs` → 202 `{runId}`, `GET /api/v1/reconciliation/runs/{id|latest}` → report `{runId, startedAt, finishedAt, status, network, safeBlock, summary{checked, matched, pending, resolvedUsed, resolvedUnused, mismatches}, suspense, items[{paymentId, paymentIntentId, runId, payer, payTo, amount, buyerState, sellerState, chainState, txHash, status MATCHED|PENDING|MISMATCH|TX_UNKNOWN, mismatch{kind, ledgerValue, chainValue, adjustmentEntryId}}]}`. Never a nonce.

## As built: audit fixes, non-ledger side
- *Orchestrator resolver:* no transaction is open during RPC reads. One runner at a time through a **session** advisory lock (`pg_try_advisory_lock`) on a dedicated connection, released in `finally`; if the unlock fails the connection is aborted. Work lists come from `PaymentIntentService.claimHeld*` (one `UPDATE ... FROM (SELECT ... ORDER BY resolution_attempted_at NULLS FIRST, valid_before, id LIMIT n)` that stamps `resolution_attempted_at`, V7), so 20 always-failing intents cannot starve the 21st. Each intent: read outside any transaction, RPC, then a short `REQUIRES_NEW` transaction that re-locks (`FOR UPDATE`), re-checks HELD and applies. HELD intents with no recorded authorization (RESERVED -> HELD: the signature never left) are released locally at once: `resolved_by = 'LOCAL'` (V7 widens the CHECK), counters released, **no payment event**; pass counts them as `released`, metric outcome `released_local`. `AfterCommit` swallows and logs (class name) a failing deferred action.
- *Seller recorder:* an upsert, not DO NOTHING: `ON CONFLICT (payment_key) DO UPDATE ... WHERE settlement.outcome = 'SETTLE_FAILED' AND EXCLUDED.outcome = 'SETTLED'`, and `PaymentSettled` (its own deterministic event id) is published on that upgrade; a settled row is never downgraded. The recorder is bounded: a `TransactionTemplate` bean with a 2 s timeout, and Hikari `data-source-properties` `socketTimeout=2`, `cancelSignalTimeout=2` (pgjdbc's default 10 s cancel wait made a 2 s query timeout take 12 s on a stalled server), `options=-c statement_timeout=2500`, `validation-timeout=1s`. `StalledDatabaseTests` pauses the Postgres container.
- *evm-rpc API additions (for the ledger):* `UsdcTransfer(from, to, value, logIndex)` (3-arg constructor keeps `logIndex = -1`); new `UsdcAuthorizationUse(authorizer, nonce, logIndex)` with `key()`; `UsdcReceipt` has a sixth component `authorizationUses` (5-arg constructor derives it with index -1), so a transfer pairs with its authorization by position within one transaction. `findAuthorizationTx` checks `topics[0..2]` itself and skips `removed` logs. `saiman.chain.rpc-url` must not carry a query or fragment. JSON-RPC errors with code -32005 or -32016 are transient (retried, breaker counts); detection by code only. sepolia.base.org's exact rate-limit answer was not verified against the live endpoint (no network in this task): HTTP 429 was already transient.
